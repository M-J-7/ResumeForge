# Cover-letter Enhance feature plan

## Status — measured 2026-09-10, and **not shipped**

The feature is built, correct, and tested. It is also **off**, and it should
stay off until the model changes: `pnpm enhance:fetch` is not run by any
deployment, so `isEnhancementInstalled()` finds nothing and the editor says the
feature is unavailable here. The deterministic Recompose — which is what the
letters are composed from in the first place, and which needs no model — is
unaffected.

That is a change of status from "implemented", and it comes from running the
model in a browser for the first time. `pnpm qa:enhance` is the pass;
`docs/QA.md` §11 holds the numbers and every proposal it produced.

### Round two: decoder models, and the same answer

The first evaluation tested the seq2seq family the plan chose. The obvious
objection was that `flan-t5` is the wrong _shape_ of model, not merely a small
one — a modern instruction-tuned decoder should do far better. So three more
were vendored and measured, on WebGPU, with a stricter prompt carrying an
explicit worked example and a "return only the paragraph" rule.

| Model                        | Size (q4f16) | Result                                                                                                 |
| ---------------------------- | ------------ | ------------------------------------------------------------------------------------------------------ |
| `SmolLM2-360M-Instruct`      | 273 MB       | Echoes the input verbatim, then appends the prompt's own `Rewritten paragraph:` label and starts again |
| `SmolLM2-360M-Instruct` (q4) | 388 MB       | Identical failures, slower                                                                             |
| `Qwen2.5-0.5B-Instruct`      | 483 MB       | Fluent, and unsafe — below                                                                             |

**Qwen is the closest anything has come, and it is still not close enough.**
Five paragraphs, warm, on WebGPU:

- One is genuinely good: _"At Northwind Payments, I replaced nightly batches
  with an event-driven pipeline, reducing settlement processing time from 40
  minutes to 6."_ That is the feature working.
- One invented a unit. Given _"cut settlement processing from 40 minutes to
  6"_, it wrote _"from 40 minutes to just over 6 hours"_ — a six-minute
  pipeline described as a six-hour one, on a job application. Both digits were
  in the evidence, so the guardrail's bare-number check passed it.
- One inverted a measurement: _"p99 latency from 1.4s to 210ms"_ became
  _"reduce latency by 210 milliseconds"_, which is a different and false claim.
- One invented prose wholesale: _"My expertise has been directly applied to
  this position, where I have successfully transformed our daily workload into
  a seamless, event-driven system."_ No new proper noun, no new number, no
  escalated verb — **nothing the guardrail can see**. It is also exactly the
  generic AI cover-letter prose D8 exists to prevent, generated by us.
- One confused whose experience it was describing: _"That is also mentioned in
  your previous experience."_

Warm latency was **14 to 38 seconds per paragraph** on WebGPU, which is not an
interaction anybody would use twice.

### What the two rounds together establish

Six models across two architectures and eight prompt shapes:
`flan-t5-small`, `flan-t5-base`, `LaMini-Flan-T5-248M`, `SmolLM2-360M-Instruct`
at two quantisations, and `Qwen2.5-0.5B-Instruct`.

**The constraint that defeats this is the local one, and it is D6, not D8.** A
model small enough to download into a browser is not reliable enough to put
sentences on a job application. The failure that settles it is not the garbage
or the echoing — those are visible and refusable. It is the fluent, plausible,
partly-invented sentence, because the guardrail is built to catch invented
_nouns, numbers and credentials_, and "transformed our daily workload into a
seamless, event-driven system" contains none of those. A rule cannot catch it;
only a reader can, and a user pressing Enhance is not reading critically — that
is why they pressed it.

Two guardrail rules came out of this round and are worth having whatever
happens to the feature, because they are provider-neutral:

- **A number's unit is part of the claim.** `quantities()` now captures the
  measure word after a figure, so `6` and `6 hours` are different quantities.
  This is the rule that catches the Qwen failure above.
- **A proposal that talks about itself is not a paragraph.** Chat models are
  trained to be helpful out loud; `looksLikeCommentary` refuses preambles,
  AI-refusal boilerplate and echoed prompt scaffolding. Every pattern in it is
  a string a real candidate model actually produced.

### Where that leaves the feature

Off, as before, and now on stronger evidence. It is one decision away from
either state and the decision is not an implementation one:

- **Delete it.** The product's argument — no model writes your resume — is
  cleaner without an AI feature attached that barely works, and the
  deterministic composer got materially better in the same session (§12).
- **Keep it dormant.** Costs nothing: no deployment vendors the weights, the
  editor says so, and the hardened guardrail is already merged. If a 1–2B
  model becomes practical in a browser, `pnpm qa:enhance` is the pass to run.

What is _not_ an option is enabling it as it stands.

### The three things the measured pass found

**1. The ONNX runtime was never vendored completely, so the feature had still
never run.** `env.backends.onnx.wasm.wasmPaths` relocates a _directory_, and
ONNX Runtime Web loads a `.mjs` glue module from it as well as the `.wasm`
binary. `fetch-enhancement-model.mjs` copied one of the two. Every attempt
downloaded 96MB of weights and then 404ed on a 44KB loader, and the user was
told "Local enhancement is unavailable right now".

This is the same shape of bug as departure 1 below, one layer down, and it
survived the fix for departure 1 for the same reason that one survived so
long: `enhance.hosting.test.ts` asserted that the _script contained a string_.
It did. Asserting the presence of a filename in a script is not asserting that
the script vendors what the runtime asks for. The script now copies every
`ort-*` file the installed package ships, and the test compares that set
against the package's actual directory listing.

**2. The WebGPU path returned one byte-identical string for every input.**

```
"comunicat cabluvêtement this this this this this this this this …"
```

The same string for four different paragraphs, which means the encoder's
output never reached the decoder at all. The same weights, the same prompt and
the same build produce ordinary English on the WASM path in one to three
seconds. int8 (`dtype: "q8"`) weights on ONNX Runtime Web's JSEP provider are
a known-bad pairing — the runtime warns that it could not assign every node to
the preferred provider, and this is what that looks like from outside.

It was invisible because **the guardrail did its job**: the garbage was
rejected as "stopped mid-sentence", so a completely broken backend presented
as a plausible failure message. A feature that is broken on every machine with
a working GPU and correct on every machine without one is worse than one that
is simply slower everywhere — so the WebGPU path is gone. WASM only.
`enhance.hosting.test.ts` pins the code; the §11 pass pins the behaviour, by
running the same paragraph in a browser with a working adapter and one without
and requiring identical output.

**3. `flan-t5-small` cannot do this task, and no prompt fixes it.**

On the working backend it echoes its input unchanged, drops facts, or emits
fragments. Six prompt shapes were tried — the shipped one, a bare paraphrase,
the T5 `paraphrase:` prefix, a single instruction with no evidence pack, a
grammar-correction framing, and the instruction after the text. Results
included `"id=0"`, a line of spaces, `"I was able to get a job at the company
and then work for the company."`, and a repetition loop.

Two larger models were tried at 278MB each:

| Model                        | Result                                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `Xenova/flan-t5-base`        | Safe and useless — returns the input verbatim for three of four paragraphs, so the guardrail rejects it as no improvement |
| `Xenova/LaMini-Flan-T5-248M` | Best single rewrite seen, and unusable: on the shipped prompt it emits _"I'm sorry, but as an AI language model…"_        |

LaMini is distilled from a model that refuses things, so it has learned to
refuse. Its one good output — turning "I cut median deploy time" into "I
reduced median deploy time", keeping every fact — is what the feature is
supposed to do, and one in four at 2.9× the download is not a bar being
cleared.

### What the pass also exposed, and was not fixed

**The guardrail catches invented claims, not removed ones.** `"Your posting
asks for Kubernetes. That is in the work above."` became `"Your posting asks
for Kubernetes."` and passed every rule: nothing was invented, no number
appeared, no verb escalated. Silently dropping half a paragraph is a real
defect and the guardrail has no rule for it.

It is recorded rather than built, deliberately. A material-omission rule needs
a threshold — how much shortening is concision and how much is loss — and the
only honest way to set one is against a model whose output is worth keeping.
Calibrating it against a model that returns `"id=0"` would produce a number
that looks measured and is not. Whoever changes the model owns this rule.

### What would have to be true to turn it on

1. A model that rewrites a paragraph without inventing, dropping or echoing,
   at a download somebody would accept for an optional feature.
2. `pnpm qa:enhance` run on real hardware, with the proposals **read**, not
   just a check that nothing threw — that is precisely what let a completely
   broken backend through.
3. The omission rule above, calibrated against that model.

## Original status note — implemented 2026-09-10

Every section below is built. The plan is kept as written because it is the
reasoning; this records where it landed and the four places the
implementation departed from it, each for a reason found while building.

| Plan section            | Where it landed                                                                                                                          |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Product decision        | D8 amendment (2026-09-08) and `src/app/privacy/page.tsx`, both already in place                                                          |
| User experience         | `LetterEditor.tsx` — consent dialog, per-paragraph Enhance, progress, Cancel, word-level diff, Apply / Keep original / Try again, Revert |
| Local model approach    | `enhance.browser.ts`, dynamically imported, pinned revision, WebGPU with WASM fallback                                                   |
| Contract and guardrails | `enhance.ts` (pure), with `enhance.test.ts`, `enhance.eval.test.ts` and `enhance.hosting.test.ts`                                        |
| Data model              | Schema v2, `migrateCoverLetter` v1→v2, `enhancement` metadata — already in place                                                         |
| Delivery and testing    | 36-case adversarial corpus incl. prompt injection; `e2e/enhance.spec.ts`; QA §11 for the measured pass                                   |

### Four departures, and why

**1. The model is self-hosted. It had to be.** The plan said the only network
request should be "the one-time static model download from the app's
configured asset origin", and the implementation fetched from
`huggingface.co`. The app's CSP is `connect-src 'self' blob: data:`, so that
request was **blocked in every production build** — the feature could never
have worked, and failed identically to a device that genuinely could not run
it. `scripts/fetch-enhancement-model.mjs` now vendors the pinned weights and
the ONNX runtime into `public/`, and the adapter sets
`allowRemoteModels = false`. That is also the stronger privacy position: no
third-party host sees the IP address of somebody writing a cover letter, and
there is no code path left that could send one anywhere.

Vendoring is ~120MB on disk and ~100MB on the wire (measured; the ~98MB
figure written here originally was wrong, and was also missing the ONNX loader
the feature could not run without). So it is a deliberate `pnpm enhance:fetch` rather than
part of `prebuild`. A build without it is a supported state: the editor probes
for the files and says the feature is unavailable on this deployment, and
Recompose is unaffected. See `docs/RUNBOOK.md`.

**2. The guardrail was failing open.** `containsTerm` case-folded the text and
searched for `" term "` with spaces around it, which silently missed every
term ending a sentence — so a proposal claiming an unsupported requirement
passed whenever the term happened to fall last. A guardrail that fails open
looks exactly like one that found nothing wrong. The tokeniser is rewritten,
and every rejection rule is now asserted in sentence-final position
specifically.

**3. "Proper-noun-like terms, tool/skill names" was specified but never
built.** Only ALL-CAPS acronyms were checked, so an invented _Datadog_ or
_Globex_ passed unless the job description happened to name it. An invented
employer is the worst thing this feature could produce, so capitalisation is
now treated as a claim.

**4. The prompt-injection test tests a different thing than the plan
implied.** The defence is not the "reference data, not instructions" line — a
small model may simply not obey it. It is that (a) raw posting text never
reaches the prompt at all, only canonical scored requirements, and (b) output
is validated regardless of what the model was told. Both are asserted
separately, so neither is load-bearing alone.

### Also fixed on the way through

- The prompt put the paragraph under edit **last**, and the tokeniser
  truncates at 512 tokens from the end. A generous evidence pack could
  therefore push the paragraph out of the window entirely, leaving the model
  rewriting nothing. The evidence budget is now derived from the window and
  asserted by a test.
- `max_new_tokens` was fixed at 180, which truncates a long paragraph
  mid-clause. It is derived from the input now, and a truncated proposal is
  rejected rather than shown.
- There was no way to cancel. A WASM beam search runs for tens of seconds;
  `InterruptableStoppingCriteria` now stops the work rather than discarding
  its result.
- Recomposing an enhanced paragraph silently discarded the enhancement and
  the `originalText` that Revert depends on. It asks first.
- The draft banner replaced "every sentence came from your resume" with the
  AI-assisted line as soon as _one_ paragraph was enhanced, understating the
  provenance of the rest. It now states both, with counts.

## Goal

After the deterministic cover-letter composer creates a draft, offer an **Enhance** action for each generated paragraph. It should improve clarity, professionalism, grammar, tone, and fit to the selected job description without inventing experience, metrics, employers, tools, credentials, or outcomes.

The enhancement must be free for every user: no paid API, account, credit limit, or server-side inference. The model runs in the browser on the user's device.

## Important product decision

This deliberately changes D8 in `docs/DECISIONS.md`, which currently prohibits any generative model in the product path, and the privacy page currently promises that no resume is sent to a language model. Before implementation, add a dated D8 amendment that permits **local-only cover-letter enhancement** under the safeguards below. The privacy copy must be changed at the same time to state plainly that the optional model runs locally, its input does not leave the browser, and it is not used for training.

D6 remains intact: guests' resumes, letters, and job descriptions stay in IndexedDB. Signed-in users may save their final letter as today, but enhancement input is never sent to our server.

## User experience

1. Keep **Compose draft** unchanged. It remains the fast, deterministic first pass and retains the current resume-source chips.
2. Add an **Enhance** button next to **Recompose** for generated paragraphs. Do not show it for `custom` paragraphs in the first release; this keeps the feature scoped to text the product generated.
3. On first use, explain that the optional enhancement model downloads once, runs on the user's device, and may take a little while. Provide **Download & enhance** and **Not now**. Cache model files with the browser Cache API/IndexedDB so subsequent uses do not download again.
4. While processing, disable the paragraph's Enhance and Recompose controls, show `Enhancing…`, and keep the original paragraph visible. An error, cancellation, unavailable WebGPU, or an unsupported browser must leave the original unchanged and offer the deterministic **Recompose** action as the free fallback.
5. Return a proposed replacement, not an automatic overwrite. Show the original and enhanced wording with an accessible word-level diff plus **Apply**, **Keep original**, and **Try again**. Applying changes only that paragraph, marks the letter dirty, and refreshes the PDF preview.
6. Change the draft banner from the absolute statement “Every sentence came from your resume” to two accurate states: deterministic paragraphs retain that statement; accepted enhanced paragraphs say “AI-assisted wording — review every claim before sending.” Keep the original sources chip and add an `Enhanced locally` badge.

## Local model approach

- Add a browser-only enhancement adapter, for example `src/lib/cover-letter/enhance.browser.ts`, behind a small `Enhancer` interface. It is dynamically imported only after the user presses Enhance, so it adds no initial bundle cost.
- Use the pinned Apache-2.0 `Xenova/flan-t5-small` ONNX model at revision `ec15bc2d425022b2de62f639b15cfea4bd9b8b3b`, through `@huggingface/transformers` 3.8.1. It is suitable for in-browser WebGPU/WASM inference and needs neither a hosted inference service nor an API key. Before broad release, record measured download size, supported browser matrix, low-spec latency, and output-quality results.
- Prefer WebGPU, with WASM as a slower optional fallback only if the measured memory and latency are acceptable. If neither is suitable, leave the feature unavailable rather than moving content to a server.
- Limit each request to one paragraph, a compact job-relevance brief, and only the resume evidence already recorded in `paragraph.sources`. This keeps device-memory use and model download needs realistic and minimizes irrelevant personal data in the prompt.
- Keep the implementation provider-neutral. A later self-hosted or paid provider may only be considered through a separate product and privacy decision; it is outside this free feature.

## Enhancement contract and guardrails

Build `src/lib/cover-letter/enhance.ts` as a pure validation layer shared by the browser adapter and tests.

- Input: paragraph text and role, selected tone, role/company, top matched job requirements, and the exact source entries/bullets identified by `paragraph.sources`.
- The instruction tells the model to preserve all factual claims; improve only wording, flow, concision, grammar, and job-description terminology that is supported by the provided evidence. It must not add facts, numbers, named tools, employers, qualifications, or a claim of proficiency not present in the source pack. No web search or external tools are available.
- Request only one replacement paragraph. Treat model output as untrusted input: trim it, cap it to the existing 4,000-character paragraph limit, and reject empty, unchanged, or materially overlong output. The review UI, not an opaque model-generated rationale, makes the alteration visible.
- Create an evidence token set from the original paragraph plus its cited resume bullets. Reject a proposal that introduces numbers, proper-noun-like terms, tool/skill names, degree/certification language, or achievement verbs not backed by that set. These checks are a guardrail, not proof; the user must still review the diff.
- Preserve the paragraph's source IDs in the document. Do not claim enhanced prose is verbatim resume text.
- Keep prompt construction and model output in memory only. Do not write prompts, responses, or raw resume text to analytics, error logs, the database, or browser telemetry. Record only local, non-content diagnostics if we later add an opt-in error report.

## Data model and editor changes

1. Bump `CURRENT_COVER_LETTER_SCHEMA_VERSION` to 2 and add the v1-to-v2 migration in `src/lib/cover-letter/migrate.ts`.
2. Extend each paragraph with optional metadata, for example `enhancement: { originalText, modelId, modelRevision, appliedAt }`. `originalText` makes Revert possible after save/reload; it is contained in the existing `content` JSON and needs no Prisma column.
3. Add `enhanceParagraph` and `revertEnhancement` callbacks to `LetterEditor.tsx`. They must only replace the targeted paragraph and set `dirty`.
4. Pass the previously computed `ComposeInput`/match result and a shared provenance lookup into the enhancement adapter. Do not reparse the job description or rescore the resume for each click.
5. Teach `ParagraphBlock` to render the action, progress/error state, local-enhancement badge, preview diff, Apply/Keep/Revert controls, and correct accessible labels. Recompose must either warn before replacing an enhanced paragraph or remove its enhancement metadata as part of replacement.
6. Update PDF, DOCX, and TXT only through their existing document renderers. They already consume paragraph text, so accepted text exports automatically; enhancement metadata must never render in an exported letter.

## Delivery sequence

1. Record the D8 amendment and update the privacy policy and editor copy; this is the explicit approval point for a local model.
2. Prototype the browser adapter outside the letter UI. Measure model-download size, first-run and warm-run latency, memory use, WebGPU/WASM behavior, and output quality on the supported browser/device matrix. Stop if the baseline is not acceptable for normal users.
3. Add schema v2, migration, provenance-source extraction, prompt builder, output parser, and claim-validation tests.
4. Integrate per-paragraph Enhance with proposal/review/revert behavior; preserve the deterministic composer as the default and fallback.
5. Test against a curated evaluation set containing varied roles, empty evidence, unusual names, dates/numbers, unsupported job requirements, and deliberate prompt-injection text inside a job description. A proposal may be polished, but it must never create a new claim.
6. Run the full verification suite and manually test guest mode, signed-in mode, saving/reloading/reverting, export, offline behavior after the initial model download, unavailable hardware, and model-download failure.

## Acceptance criteria

- Compose remains instantaneous and fully local; no enhancement runs unless the user clicks it.
- No `OPENAI_API_KEY`, paid service, account gate, server endpoint, or usage quota is introduced.
- Network inspection for both a guest and signed-in user shows no resume, job-description, or letter text sent during Enhance. The only possible feature network request is the one-time static model download from the app's configured asset origin.
- A user can accept, reject, retry, or later revert every enhancement before it changes the saved letter.
- Enhanced text retains the original provenance IDs, passes structural validation, saves/loads through migration v2, and exports without metadata.
- Automated tests reject deliberately invented metrics, tools, credentials, employers, and unsupported job keywords; e2e tests cover the review flow and unsupported-device fallback.
